## User Constraints (from CONTEXT.md)

### Locked Decisions

- Phase sequencing:
  - This is an inserted phase after Phase 8, independent from completing Phase 8.
- Delivery sequencing:
  - First deliver backend + table foundations.
  - Then deliver threshold line rendering + custom alarm UI.
- Table/UX:
  - Chart sensor table must support vertical + horizontal scroll inside the table area only.
  - Sticky header is required.
  - First column (sensor name) must stay visible (sticky first column).
  - Missing values render as `N/A`.
- Columns and filters:
  - App-level column filter is global in behavior (not per-user personalization in this phase).
  - Runtime selection restores from localStorage on reload.
  - Repo-versioned default columns are source-controlled.
  - Column defaults will be tuned after user trials.
- Data semantics:
  - `last value` = last point inside current chart range.
  - `-1d AVG` is always computed from timeseries data (never taken from sub_attributes).
  - Threshold line rendering must not be blocked by unit mismatch.
  - Show threshold unit and base sensor unit independently when available.
- Threshold line behavior:
  - HiHi + LoLo are red dashed lines.
  - Hi + Lo are yellow dashed lines.
  - Threshold lines are off by default and user-controlled by table toggles.
  - Table uses one toggle per threshold column per sensor row.
  - Toggled thresholds are rendered as additional rows in the table.
  - Threshold rows show `N/A` for unavailable context fields.
  - If a second tag is added to a chart, threshold lines are removed from that chart.
  - If the chart returns to one tag later, thresholds remain off until user re-enables.
- Custom alarms:
  - Right-click option must be available for all sensors: `Create custom alarms`.
  - One custom pair per sensor: `Custom-Hi` and `Custom-Lo`.
  - Custom alarms coexist with system thresholds (separate selectable columns/lines).
  - Persist audit/history data:
    - `created_date` (first creation),
    - `updated_date` (last user edit),
    - `version_n`,
    - stored values for `Custom-Hi` and `Custom-Lo`,
    - user fixed as `unknown` in this phase.
  - Keep version history capped at 20 versions per attribute.
- Persistence:
  - Use SQLite only in this phase.
  - SQLite filename should be custom-alarms related.
  - Export/import is deferred.
  - SQLite location approved: `backend/app/data/custom_alarms.db`.
- Duplicate normalization rule (sub_attributes):
  - Prefer non-null value.
  - Tie-break by `is_external = false`.
  - Final tie-break by newest `updated_at`.
- Threshold row format:
  - Approved label format: `{Sensor Name} | {ThresholdName}`.
- Column manifest format:
  - Repo default-column manifest is JSON.
- Custom alarm key scope:
  - Key is `attribute_id` only (global reuse across items that share attribute_id).

### Proposed Normalization Pipeline

1. Fetch raw attribute records for each chart tag `attribute_id` from workspace attribute payload including `sub_attributes`. [ASSUMED]
2. Flatten relevant threshold candidates from `sub_attributes` into canonical keys: `hihi`, `hi`, `lo`, `lolo`, plus custom keys `custom_hi`, `custom_lo`. [ASSUMED]
3. Apply locked duplicate tie-breakers per threshold key:
   - Prefer non-null `value`.
   - Prefer `is_external == false`.
   - Prefer newest `updated_at`.
   [VERIFIED: locked decisions in .planning/phases/08.1-improving-context-from-attributes/08.1-CONTEXT.md]
4. Compute timeseries-derived fields for each sensor row:
   - `last_value`: last point in current chart window.
   - `avg_1d`: computed from timeseries only, window `(chart_end - 1 day, chart_end)`.
   [VERIFIED: locked decisions in .planning/phases/08.1-improving-context-from-attributes/08.1-CONTEXT.md]
5. Any unresolved field becomes `N/A` in response payload (not `null` in rendered UI). [VERIFIED: locked decisions in .planning/phases/08.1-improving-context-from-attributes/08.1-CONTEXT.md]

## Persistence Schema Proposal (custom alarms/versioning)

**DB path:** `backend/app/data/custom_alarms.db`. [VERIFIED: locked decisions in .planning/phases/08.1-improving-context-from-attributes/08.1-CONTEXT.md]

### Tables

```sql
CREATE TABLE IF NOT EXISTS custom_alarm_current (
  attribute_id TEXT PRIMARY KEY,
  custom_hi REAL NULL,
  custom_lo REAL NULL,
  created_date TEXT NOT NULL,
  updated_date TEXT NOT NULL,
  version_n INTEGER NOT NULL,
  user TEXT NOT NULL DEFAULT 'unknown'
);

CREATE TABLE IF NOT EXISTS custom_alarm_versions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  attribute_id TEXT NOT NULL,
  version_n INTEGER NOT NULL,
  custom_hi REAL NULL,
  custom_lo REAL NULL,
  created_date TEXT NOT NULL,
  updated_date TEXT NOT NULL,
  user TEXT NOT NULL DEFAULT 'unknown',
  values_json TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_custom_alarm_versions_attr_version
  ON custom_alarm_versions(attribute_id, version_n DESC);
```
[ASSUMED]

### Write algorithm

1. Begin transaction.
2. Read current row by `attribute_id`.
3. Insert or update `custom_alarm_current` with incremented `version_n`.
4. Insert snapshot row into `custom_alarm_versions` with `values_json`.
5. Delete overflow history beyond newest 20 (`attribute_id` scoped).
6. Commit.
[VERIFIED: locked decisions in .planning/phases/08.1-improving-context-from-attributes/08.1-CONTEXT.md] [ASSUMED]

### Operational SQLite recommendations

- Use parameterized SQL placeholders (`?`) for all user-provided values. [CITED: https://docs.python.org/3/library/sqlite3.html]
- Consider enabling WAL mode for better read/write overlap under UI polling and edits. [CITED: https://www.sqlite.org/wal.html]

## Performance Risks and Mitigations

| Risk | Why It Matters | Mitigation |
|---|---|---|
| Cold `timeseries-batch` cost for large tag sets | Context already flags cold-path overhead; table enrichment can multiply fetch load. [VERIFIED: .planning/phases/08.1-improving-context-from-attributes/08.1-CONTEXT.md] | Use one sensor-context batch per chart refresh and reuse existing frontend/backend cache keys by date window/tag set. [VERIFIED: frontend/charts/services/api-client.js] [VERIFIED: backend/app/services/profiling_adapter.py] [ASSUMED] |
| Recomputing `-1d AVG` per sensor naively | N x extra queries can block UI for charts with many tags. [ASSUMED] | Compute from already fetched points when chart range includes last day; otherwise do one extra compact batch window for all tags. [ASSUMED] |
| Large table DOM + sticky cells | Many rows + sticky headers can trigger layout/repaint churn. [CITED: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/position] | Limit rendered rows to active chart tags + selected threshold rows; avoid full rerender on each hover/zoom. [ASSUMED] |
| SQLite write contention on rapid edits | Single-file DB can return busy under concurrent writes. [CITED: https://www.sqlite.org/wal.html] | Short transactions, retry-on-busy, optional WAL mode, and parameterized statements. [CITED: https://www.sqlite.org/wal.html] [CITED: https://docs.python.org/3/library/sqlite3.html] [ASSUMED] |
| Existing chart interaction regression | `chart-card` already has complex runtime state (zoom/pins/hidden series). [VERIFIED: frontend/charts/components/chart-card.js] | Keep threshold toggle state isolated from interaction state and add regression test tasks around refresh/tag edits/date changes. [ASSUMED] |
